# Build orchestration

This is the execution contract for ADR 0002. It is not part of the published
v0.1.0 engine. Package versions, the normative rules baseline and execution
compatibility identifiers are versioned separately.

## Compatibility

Configuration schema 1 retains its existing fields, defaults and unknown-field
rejection. Schema 2 adds an optional `build` table to each artifact. Schema 1
rejects that table, including an empty table. `standards_version` still identifies
the normative 0.1.0 baseline; it is not an engine compatibility identifier.
Execution plans, results and success receipts have independent schema version 2
(including compiler variants and declared environment); earlier source-development
schema 1 execution receipts must be rebuilt, never inferred compatible.
Prepared seals generated by this engine use schema version 2. They retain source
file hashes and complete inventories locally for stale/tamper checks, but SBOM
metadata contains only build identity and effective features. It contains no
source file list, per-source hash or aggregate source-input digest. Schema 1 seals
remain readable with their original verification rules for existing artifacts;
new builds never generate that legacy SBOM metadata. Git revision identity and
explicit actually shipped asset/component evidence remain distinct from a source
inventory. No package/release version changes are implied by this schema change.
The orchestration entry/engine protocol is `craftguild-execution-1`; a launcher
must verify that protocol before dispatch. ADR 0005 release preparation receipts use schema 2 to retain explicit-MAJOR intent.

## Selection and drivers

Build and prepare resolve one immutable context per selected artifact. Explicit
CLI selectors take precedence over environment, artifact build configuration,
then defaults. Selectors are artifact, toolchain, target, profile, requested Cargo
features, default-feature policy and target directory. The environment forwarding
names are `ARTIFACT`, `TOOLCHAIN`, `TARGET`, `PROFILE`, `FEATURES`,
`NO_DEFAULT_FEATURES`, and `CARGO_TARGET_DIR`. Defaults are all configured
artifacts, the available Cargo toolchain, the compiler host (Rust) or `browser`
(frontend), release, configured features and `target`. Features replace requested
features; effective Cargo root features are resolved by the driver and sealed.
Only debug and release are supported. Frontend selection never probes Rust.
Toolchain selection uses an already-installed `rustup run` toolchain; build does
not install toolchains or SDKs. Configuration paths stay repository-relative;
an explicit environment/CLI target directory may be absolute.

Rust produces `<target-dir>/<target>/<profile>/<command>` (with the platform
executable suffix). Cargo compiles in a repository-local candidate cache; the
engine publishes the verified binary to that public location. Frontend output
is its exact declared bundle tree. Build and install share this resolver. Every
artifact may declare preparation `dependencies` by artifact id; the engine
topologically orders them and rejects missing dependencies and cycles.

Execution has no implicit elapsed-time deadline. An explicit build/prepare
`--timeout SECONDS` bounds each invoked command; ordinary test/check imposes no
one-hour cap. Product watchdogs remain independent. On cancellation, send TERM
and allow five seconds for command wrappers to reap nested owned sessions before
forcing the original group to stop and verifying its termination.
Observe leader exit without reaping it, retain its PID through the final group
signal, then reap with a bounded cleanup wait. Unknown wait ownership fails
cleanup without signaling a potentially reused number. Never send another
termination signal after reaping; later group probes may only prevent rollback.

Schema 2 also allows a build `output` template below the selected target
directory. Substitutions are `{target}`, `{target_path}`, `{profile}`, `{command}`
and `{exe}`. `target_path` is `<target>/` when a target was explicitly selected,
otherwise empty; this preserves native products which omit the host directory.
The default template is `{target}/{profile}/{command}{exe}`. No traversal or
unknown substitutions are accepted. Install renders the same template using
receipt facts without probing a tool. A build may declare named `variants` with
`id`, optional `target`, `output`, compiler argv prefix and environment overrides.
CLI `--variant` or `VARIANT` selects one; a variant never silently selects itself.
Aliases can select distribution layouts and existing cross drivers such as
`cross` or `cargo xwin`, while standards still appends the selected package,
target/profile/features, invokes the compiler and verifies/publishes its output.
Base `compiler` defaults to `["cargo"]`; `environment` declares literal compiler
environment values with the same path/context substitutions. These declarations
cannot overwrite engine context or its Cargo cache routing. SDKs and cross tools
remain preinstalled prerequisites, and platform/network checks stay product gates.

`output_root` defaults to `target-directory`. `repository` instead anchors the
relative output template at the explicit repository root. Base, target and variant
settings may select it. This retains fixed distribution slots such as
`target/dist/<target>/<file>` even when `CARGO_TARGET_DIR` selects another compiler
output directory. The same resolver and receipt checks apply during install.

Optional `build.targets` entries select settings for an exact named target, with
`cross_only = true` when they apply only away from the recorded compiler host.
They may override compiler prefix, output and environment; explicit variant
overrides are applied last. This preserves both native host layouts and existing
`TARGET=<foreign-target>` dispatch without putting target detection in Make.
Compiler host/version are observed once in build context, checked again at the
prerequisite/seal boundary, and supplied to hooks as `CRAFTGUILD_HOST`. Install
uses those recorded facts and performs no compiler observation.

Rust library artifacts declare `build.library` with the real Cargo target `name`
and a nonempty `formats` array (`cdylib`, `staticlib`, `rlib`). The common graph
validates that target and preserves declared package licenses. Preparation uses a
library metadata component and the same seal/profile rules; compilation uses
`--lib`. Standards resolves each platform filename, verifies every declared
output and publishes them together. The default output template is
`{target}/{profile}/{file}`; `{file}` is the resolved executable or library filename.
Library metadata may declare extra component `properties` for retained product
evidence. This replaces duplicated library graph/preparation engines without
changing product ABI or inventing a library CLI. Host executables must return
the exact sealed SBOM; library and cross-target outputs must contain those bytes.
Host/runtime acceptance for foreign platforms remains separate. Install selects
executable artifacts only; library packaging has explicit artifact outputs.

## Hooks and execution order

`artifacts.build` declares optional `toolchain`, `profile`, `target_dir`,
`dependencies`, and `hooks`. Hooks have unique portable `id`, `stage`, argv,
`inputs`, `input_dirs`, `outputs`, `output_dirs`, and optional `depends_on` hook
ids. Stages are prerequisite, prepare, evidence and verify. Dependencies must
refer to hooks in the same or earlier stage; cycles fail before execution.
Verify hooks consume inputs but do not declare outputs. Prerequisites normally
only verify; a prerequisite may own an `environment_output` JSON file included in
its declared outputs. That file maps environment names to literal values, is
sealed as input evidence and is applied once to subsequent steps. Engine context
and Cargo cache routing cannot be overridden. `unset_env` names apply only inside
that bounded hook process, allowing a product's preflight to inspect a clean
compiler environment while still receiving all `CRAFTGUILD_*` context values.
Prepare/evidence hooks declare at least one output. No shell DSL or eval is
provided. Product hooks own a single specialized operation, never the common
prepare/seal/compiler/receipt sequence.

The engine orders prerequisite hooks, prepare hooks and required npm assets,
evidence hooks, runtime dependency resolution and ownership evidence, SBOM
validation/sealing, compiler, verify hooks, output verification, then publication.
argv is executed from the explicit repository root. Hook environment includes
`CRAFTGUILD_ARTIFACT`, `CRAFTGUILD_TOOLCHAIN`, `CRAFTGUILD_TARGET`,
`CRAFTGUILD_PROFILE`, `CRAFTGUILD_FEATURES` (JSON array),
`CRAFTGUILD_TARGET_DIR`, `CRAFTGUILD_PREPARED`, and `CRAFTGUILD_RUN`.
`CRAFTGUILD_VARIANT` identifies an explicitly selected variant or is empty.
`CRAFTGUILD_OUTPUTS` and `CRAFTGUILD_CANDIDATES` are JSON arrays of the resolved
public and candidate outputs. The singular `CRAFTGUILD_OUTPUT` and
`CRAFTGUILD_CANDIDATE` identify the first output for a bounded product verifier.
`CRAFTGUILD_COMMAND` identifies the public command whose per-run prepared record
is selected. Consumer build scripts apply `CRAFTGUILD_PREPARED` to that command;
other local artifact build scripts use their own prepared record. When the marker
is absent, the existing explicit-prepared override behavior is retained. This
prevents a root library build from assigning its seal to dependency libraries.
The run's environment evidence and receipt record only explicitly declared and
engine-provided environment facts, never the full inherited environment.
The plan and process records contain effective argv and context, not the complete
inherited environment or secrets.

Declared inputs must exist before the hook and remain byte-identical through it.
Output paths must be disjoint from inputs and from other hook-owned outputs.
The engine backs up and clears declared outputs before execution, requires fresh
regular files/directories after exit zero, inventories complete output trees and
seals those facts. Later mutations invalidate the invocation. Existing generated
ownership and isolated reproduction gates remain required; the hook's input/output
hashes do not replace generator provenance or ABI verification. Derived ownership
conversions belong under `.craftguild/`, outside tracked release inputs.
Run results retain each hook's consumed/produced hashes and inventories locally.
Later steps cannot silently change an earlier hook's evidence before sealing;
configuration, artifact manifest and lockfile are guarded across preparation too.
These developer records never become source-list properties in the SBOM.

## History, cancellation and publication

Each invocation creates `.craftguild/<command>/runs/<id>/plan.json`, ordered step
results and process output. The run id distinguishes attempts; array order defines
step ordering and UTC epoch milliseconds record times. A step moves from pending
to running to succeeded, failed or cancelled; dependent steps never start after
failure. Results record the error and failing argv, including missing tools.
The final run state is succeeded, prepared, failed or cancelled. Prepare alone
cannot create an artifact success receipt.

An exclusive repository-local lock prevents concurrent mutation. Staging owns
candidate Rust output and a rollback snapshot of declared generated outputs.
Failure or cancellation restores those outputs and leaves the prior published
binary/receipt intact. A new invocation never treats the old receipt as its own
success. The success receipt is published last after input, SBOM and output
verification. On publication I/O failure, replacements roll back. Interrupted
publication must be recovered before another mutating invocation; never infer success
from an incomplete run. Logs and failed attempts remain as technical history.

Cancellation must stop the current subprocess and its descendants, wait for
termination, restore snapshots and record cancellation. Timeout and cooperative
cancel-file behavior are tested with real subprocesses. Platform signal behavior
is an explicit acceptance boundary and must be reported when unverified.

Every subprocess exit path closes its owned Unix process group, including a
nonzero or successful leader exit with background descendants. Group termination
must be confirmed before rollback. A pending/PID scope marker also prevents
recovery from treating missing process-log evidence as proof of termination.
Unverified cleanup defers rollback and retains its snapshot. Hooks must stay in
the owned group and must not daemonize or detach into another process scope.
On macOS, signalling a zombie-only group may return `EPERM`. Inspect only that
owned group's states and accept confirmed terminal zombies; live members,
inspection errors or ambiguous empty results still prevent rollback. Confirm an
empty group's disappearance with `ESRCH` rather than treating `EPERM` as absence.
This engine currently refuses non-Unix subprocess execution before spawn;
Windows requires an equivalent OS-owned process-tree implementation and host
qualification before its execution/rollback guarantees can be offered.

This applies design-baselines at the transient technical scope: ordered execution
history and immutable success receipts retain provenance. There is no persistent
business entity or business line-item aggregate. No business state table,
Header-Detail database, ORM or product model change is required.

## Success receipts and install

A receipt contains protocol/schema identifiers, run id, resolved context, exact
prepared seal, SBOM digest and output file hashes. Input inventories detect both
changes and additions. Install requires a matching existing receipt and output,
checks selectors without compiler/toolchain probes, verifies sealed inputs and
SBOM and copies only the existing output. Missing engine, cache, receipt or binary
fails with nonprivileged setup/build instructions. Install must never bootstrap,
invoke Cargo/npm, resolve dependencies or acquire tools.

`PREFIX` defaults to `/usr/local`, `BINDIR` to `<prefix>/bin`; `DESTDIR` is a staging
root prepended to the absolute bindir. CLI destination flags override environment.
Install validates target/profile/features/toolchain/output-directory selection
against the receipt, and rejects tampering or mismatched settings.
Install reads and verifies one captured output byte sequence before copying it.
It does not take the mutating execution lock or recover build state, so an
acceptance gate can verify/install its completed build without probing processes
or blocking behind its own parent operation. Concurrent publication cannot replace
the captured bytes with an unchecked second read; a receipt/hash mismatch fails.

## Standalone entry and dispatch

ADR 0004 replaces execution/skill archives with a fixed release reference and
small shared entry. See [initialization](initialization.md) for schema 3 reference
ownership, embedded context, entry protocol, acquisition, cache validation and
rollback. Entry compatibility is `craftguild-entry-1`; execution receipts retain
`craftguild-execution-1`. Only init and explicit setup may acquire an engine;
ordinary operations never compile/download a replacement or resolve Latest.

Delivery first validates complete prepared seals, exact inventories and their
sealed-file linkage, SBOM and outputs through the common receipt/package owner.
Changed or added build inputs invalidate delivery until rebuild. Flat binaries,
matching SBOMs, checksums and versioned host metadata replace both archives.
Detailed source integrity ledgers stay producer-local.

Make, CLI and CI dispatch build/prepare/install/test/check/acceptance/release to
the same engine. Test executes ordinary adapter/repository test gates; check
retains the existing global quality semantics and changed-scope behavior;
acceptance executes only explicitly requested acceptance gates. Release delegates
to existing internal Conventional Commits/SemVer/OpenPGP preparation, retaining
all pending-release and planned-file guards. Product aliases only forward.
`acceptance --gate ID` selects one declared acceptance command. The common Make
entry forwards `ACCEPTANCE_ARGS`, so separate public acceptance aliases retain
their scope without running another artifact's host/service gate. Unknown ids fail.

Schema 2 root `operations` entries describe required preparation around `test`,
`check`, `acceptance` or `release`. Each has a unique `name`, a context `artifact`,
optional `prepare` and `build` artifact-id lists and bounded `hooks` using the
same declaration contract. Their order is prerequisite/prepare hooks, declared
artifact preparation/build (including dependencies), evidence hooks, the existing
operation gates, then verify hooks. These lists cannot configure install;
installation always follows the copy-only path. Unknown operation names and
duplicate/missing artifact ids fail configuration validation. Schema 1 rejects
the `operations` field even if empty.

The operation has its own plan/results and rollback snapshot of hook-owned
outputs, with `CRAFTGUILD_OPERATION` naming the action. It does not create an
artifact success receipt. Each successful declared build retains its own receipt;
a later gate failure belongs to the operation, never to that earlier build.
Ownership conversion can therefore run before global quality assessment and its
exact regeneration checks without living in a product Rust engine. Without an
operation declaration, existing dispatch semantics and gate scopes apply.

## Canonical outputs and release packaging

Standard Rust layout and declarative standalone installers use schema 2.
Build, copy-only install and package share the resolved
context and complete receipt verification. Inferred install targets retain the
receipt's explicit-target layout fact; an explicitly different selector still
fails. Standard mode has no old-path search or compatibility copies.

`installer` is deterministic generation (or read-only comparison). `package` is
read-only source verification followed by a staged directory rename. It verifies
the current explicit Git root is clean at the full revision recorded by every
clean release receipt, the group's version authority, matching targets, complete
seals/inventories, SBOM bytes and output hashes. It packages receipt outputs into
`<command>-v<version>-<target>`, matching `.bom.json` files and
`SHA256SUMS-<target>.txt`. Existing destinations are refused. It never invokes a
compiler or dependency resolver. Entry dispatch requires a verified engine cache,
just as copy-only install does. Make forwards `INSTALLER_ARGS` and `PACKAGE_ARGS`
to the same CLI operations.

Installer download, verification, staging and rename are transient technical
stages. Traps clean owned temporary paths, and the old command survives failed
verification or placement. No persistent business state, transition table,
Header-Detail aggregate or install registry is introduced. Producer receipts remain
local provenance; consumer artifacts do not gain source inventories or hashes.
